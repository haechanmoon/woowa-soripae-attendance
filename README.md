# 소리패 시스템

밴드 동아리 **소리패**의 합주 출석을 관리하던 웹 앱입니다. 토이 프로젝트가 아니라 **부원 25명이 매일 쓰던 운영 서비스**였습니다. 출석 인증, 지각·결석 벌금 계산, 합주 스케줄 조율, 임원진 관리 기능이 들어 있습니다.

기존에는 카카오톡으로 "저 왔어요" 사진을 올리고 임원이 수기로 지각 시간을 세어 벌금을 계산했습니다. 사람이 세는 이상 기준이 흔들리고 기록이 남지 않는 게 문제였습니다.

> **운영 종료 (2026-08-22)**
> 서비스 목적이었던 하계 공연이 끝나 EC2 인스턴스를 정리했습니다. 종료 전에 DB 전체와 접속 로그 32일치, 서버 설정을 백업했고, 복구 절차는 문서로 남겼습니다. 방치가 아니라 계획된 종료입니다.

---

## 운영 기록

**2026년 7월 20일 ~ 8월 22일 (34일간 운영)**

| 항목 | 수치 |
|---|---|
| 등록 부원 | 25명 |
| 출석 인증 | 106건 |
| 연습 스케줄 등록 | 101건 |
| 누적 접속자 | 173명 (고유 IP) |
| 최다 접속일 | 28명 (7/24) |
| 배포 | 10회 이상 |
| 커밋 | 35개 |
| 테스트 | 139개 |

접속자 수는 **서버 로그의 고유 IP 기준 추정치**입니다. 정확한 DAU가 아닙니다 — 같은 와이파이를 쓰면 여러 명이 한 명으로 합쳐지고, 데이터 통신은 IP가 바뀌어 한 명이 둘로 셉니다. 실제로 부원이 25명인데 하루 접속자가 28명으로 잡힌 날이 있습니다. 이 한계를 알고 추세 파악용으로만 썼습니다.

사용량은 공연 준비가 몰린 7월 말에 정점을 찍고 공연 이후 자연스럽게 줄었습니다. 서비스의 수명이 실제 행사 주기와 그대로 겹칩니다.

접속 통계는 브라우저에 심는 분석 도구 대신 **서버 로그를 직접 집계**했습니다. 이 앱은 광고 차단기 때문에 API가 막힌 줄 알고 헤맨 전력이 있어서, 클라이언트에서 수집하면 상당수가 집계에서 빠지기 때문입니다. 집계기는 `ops/soripae-stats.sh`에 있고 매시간 정적 HTML을 생성했습니다.

## 운영하면서 틀렸다가 고친 것들

이 저장소에서 가장 볼 만한 부분입니다. 전체 기록은 **[docs/decisions.md](docs/decisions.md)** 에 있습니다.

**광고 차단기 탓인 줄 알고 API 경로를 두 번 바꿨다**
부원들에게서 "Failed to fetch"가 뜬다는 제보가 왔고, `/api/events`가 404였습니다. 광고 차단기가 `events`를 막는다고 판단해 경로를 `/api/club-events`로, 다시 `/api/performances`로 바꿨습니다. 둘 다 헛수고였습니다. 진짜 원인은 **정적 파일에 `Cache-Control` 헤더가 없어 브라우저가 옛 JS를 계속 캐싱**한 것이었고, 크롬에서도 재현됐습니다. 가설이 그럴듯하다고 검증을 건너뛰면 두 번까지도 틀릴 수 있다는 걸 배웠습니다.

**테스트가 실제 DB를 건드리고 있었다**
`@SpringBootTest`가 로컬 MySQL에 그대로 붙어서 `./gradlew test`만 돌려도 Flyway 마이그레이션이 실행됐습니다. 실제로 V6가 그렇게 적용됐습니다. 파괴적인 마이그레이션이었다면 테스트를 돌린 것만으로 진짜 데이터가 지워졌을 상황이라, 테스트를 인메모리 H2로 완전히 떼어냈습니다.

**데이터를 지우는 마이그레이션을 운영에 돌렸다**
"하루 한 번 인증하면 출석 인정"으로 규칙을 바꾸면서 유니크 키를 (부원, 날짜)로 축소해야 했고, 제약을 걸기 전에 중복 행을 정리해야 했습니다. 운영 데이터 41건이 34건이 되는 마이그레이션이라 **삭제될 행을 먼저 뽑아 보여주고 승인을 받은 뒤** 적용했습니다.

**통계를 만들었더니 통계가 봇이었다**
전체 요청의 74%가 404였고 스캐너 하나가 하루 3만 건을 때린 적도 있습니다. 처음엔 "요청 200건 초과"로 걸렀는데 40~200건짜리 중소형 스캐너가 다 빠져나가 새벽 시간대가 부풀었습니다. 기준을 건수가 아니라 **행동**으로 뒤집었습니다 — 로그인 화면(`/api/members`)을 한 번이라도 부른 IP만 사람으로 봅니다. 앱을 열면 반드시 거치는 요청이라 사람이면 무조건 남고, 스캐너는 이 주소를 모릅니다.

## 기술 스택

**백엔드** · Java 21, Spring Boot 4.1, Spring Data JPA, Flyway, MySQL 8
**프론트엔드** · 바닐라 JS + Tailwind (SPA, 빌드 도구 없음), PWA
**인프라** · AWS EC2 (t3.micro), Nginx 리버스 프록시, Let's Encrypt HTTPS, systemd

프론트엔드에 프레임워크를 쓰지 않은 건 의도적입니다. 화면이 10개 남짓이고 실사용자가 25명인 규모에서 빌드 파이프라인을 들이는 비용이 이득보다 크다고 봤습니다.

도메인은 `soripae.duckdns.org`를 썼습니다. sslip.io 대신 DuckDNS를 고른 이유는 **부원이 비개발자**라, 숫자로 된 주소나 브라우저의 "안전하지 않음" 경고가 접속 자체를 막을 수 있다고 봤기 때문입니다.

## 도메인 규칙

출석과 벌금 정책이 이 서비스의 핵심입니다. 규칙이 한 곳에만 있도록 `FineCalculator`에 모아두었습니다.

- 정규 연습(코어타임)은 **13시 시작**
- **하루에 한 번 인증하면 그날 출석 인정.** 곡이 여러 개여도 한 번이면 끝
- 지각 기준 시각은 서버가 정합니다 — 그날 등록한 스케줄이 있으면 그 시각, 없으면 코어타임 13시
- 지각은 **분당 100원**, **60분 이상 늦으면 결석**으로 처리하고 **6,000원** 정액
- 스케줄 등록은 **다음 주만** 가능하고 마감은 일요일 자정. 마감이 지난 이번 주는 사유를 남겨야 바꿀 수 있습니다

## 구조

```
domain/          비즈니스 규칙. 웹 계층을 모른다
  attendance/      출석 인증, 벌금 계산 (FineCalculator)
  schedule/        합주 스케줄, 주 단위 집계 (WeekScope)
  member/          부원
  song/            곡 배정, 합주 시간 조율
  event/           공연·행사
web/             REST 컨트롤러 + 요청/응답 DTO
global/          예외 처리, 파일 저장, 설정
resources/
  db/migration/    Flyway 마이그레이션 (V1~V6, V4 결번)
  static/          SPA (HTML 1개 + JS 모듈 9개)
ops/             운영 스크립트 (접속 통계 집계기, 체인지로그 렌더러)
docs/            결정 기록, 배포 이력
```

도메인 계층은 웹 계층을 참조하지 않습니다. 날짜 계산처럼 규칙이 얽히는 부분은 `WeekScope` 같은 값 객체로 빼내 요일 7개를 전부 넣어 검증합니다 — 구현을 그대로 베껴 기대값을 만들면 테스트가 아무것도 잡지 못하기 때문입니다.

## 테스트

```bash
./gradlew test     # 139개
```

테스트는 **인메모리 H2**를 쓰고 Flyway를 끕니다. 마이그레이션 SQL은 MySQL 전용 문법(`ENGINE=InnoDB`, `DELETE ... JOIN`)이라 H2에서 그대로 돌지 않고, 여기서 검증할 대상도 아닙니다. 스키마와 엔티티가 맞는지는 앱이 실제로 뜰 때 `ddl-auto=validate`가 잡아줍니다.

## 로컬 실행

```bash
# MySQL에 soripae_attendance 스키마가 있어야 합니다. Flyway가 나머지를 만듭니다.
ADMIN_PASSWORD=원하는값 ./gradlew bootRun
```

`ADMIN_PASSWORD`는 **기본값이 없습니다.** 이 저장소는 public이라 설정 파일에 적은 값은 그대로 공개되기 때문입니다. 넘기지 않으면 임원 로그인이 전부 거부됩니다(fail closed) — 환경변수를 빠뜨린 배포가 무인증 상태가 되는 것보다 낫다고 봤습니다.

DB 접속 정보도 `DB_URL` / `DB_USERNAME` / `DB_PASSWORD` 환경변수로 덮어쓸 수 있습니다.

## 운영 종료와 보존

2026년 8월 22일, 하계 공연 종료와 함께 EC2 인스턴스를 종료했습니다. 중지가 아니라 종료라 디스크가 함께 삭제되므로, 그 전에 아래를 백업했습니다.

- **DB 전체 덤프** — 부원·출석·스케줄·곡 등 전 테이블, `flyway_schema_history` 포함
- **Nginx 접속 로그 32일치** — 통계의 원본 데이터. 이게 없으면 집계기만 남고 먹일 게 없습니다
- **생성된 통계 페이지** — 외부 의존성 없는 단독 HTML이라 오프라인에서도 열립니다
- **서버 설정** — Nginx conf, systemd 유닛 5개(앱 / 통계 타이머 / 인증서 갱신 타이머)
- **인증 사진** 11장

인증서와 설치 패키지는 백업하지 않았습니다. 재발급·재설치가 가능한 것들이라 보관할 이유가 없다고 봤습니다.

**이 프로젝트에서 가장 늦게 깨달은 것이 백업이었습니다.** 로컬 개발 DB와 운영 DB 사이에 자동 동기화나 백업 파이프라인이 처음부터 없었고, 종료를 결정하는 시점에야 그게 드러났습니다. 다시 만든다면 **파일은 서버 디스크가 아니라 S3에, DB는 스냅샷 일정을 걸어두고** 시작하겠습니다. 그러면 서버를 내리는 일이 백업 작업이 아니라 그냥 버튼 하나가 됩니다.

## 알려진 한계

솔직하게 적어둡니다. 규모로 승부하는 프로젝트가 아닙니다.

- **임원 인증이 공유 비밀번호 하나**입니다. 토큰이나 세션을 발급하지 않아서, 이 검증을 통과한 뒤의 임원 전용 엔드포인트는 여전히 무인증입니다. 부원 25명의 신뢰 관계 안에서 MVP 마감을 맞추려고 받아들인 타협이고, 더 넓게 쓸 거라면 가장 먼저 고쳐야 할 부분입니다 (`AdminAuthController` javadoc에 명시).
- 배포가 **수동 `git pull` + `systemctl restart`** 입니다. CI/CD가 없습니다.
- 서버 **1대**, 로드밸런서나 이중화가 없습니다. 배포하면 앱이 뜨는 몇 초 동안 502가 납니다.
- 커밋 히스토리에 **임원 비밀번호 기본값이 평문으로 남아 있습니다.** 현재 코드에서는 제거했지만 과거 커밋에는 남아 있습니다. 서비스가 종료돼 실제 위험은 없지만, 처음부터 환경변수로만 받았어야 했습니다.
